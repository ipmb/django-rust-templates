# M18.1 — Self-hosting `_impl`, and the `TEMPLATES` backend Implementation Plan

> **Superseded in two names: the package is `engine/` and the module is `rust.py`.**
> This plan was dispatched naming `django_rust_templates._impl` and
> `django_rust_templates.backends.RustTemplates`, and both paths were correct when it
> was written. They are not correct now. `_impl/` is
> `python/django_rust_templates/engine/` (M18.1, `511d79e`), and `backends.py` is
> `python/django_rust_templates/rust.py` (the round after M18.2) because
> `EngineHandler.default_name` derives the engine's alias from the *second-to-last*
> segment of the backend path, and `backends` is not the name anyone reaches for.
> Every `_impl` and every `backends.py` / `django_rust_templates.backends` below is
> that stale path left as written; the files they name are `engine/` and `rust.py`,
> and `scripts/check_packaging.sh` drives the current path.
> `.review/m18-record.md` §2.2 is the record of the rename.
>
> **Two of those three have a commit and the third does not**, which is worth
> saying rather than leaving to be inferred from the presence or absence of a hash:
> `511d79e` is the engine rename, the record is a file, and the `backends.py` →
> `rust.py` rename is **staged and uncommitted** in the working tree — `git log --
> python/django_rust_templates/rust.py` prints nothing, so no hash can be named for
> it and this note does not invent one. **Nothing in this tree would have caught
> either stale name in this file.** The anchor gate is the only reader of prose in
> the repository and its roots are `crates`, `python`, `tests` and
> `docs/superpowers/specs`; `docs/superpowers/plans/` and `.review/` are excluded
> on purpose, for the reason recorded beside the exclusion in
> `scripts/check_python_anchors.py` (a plan describes what was about to be done and
> is left as written). So this blockquote is a manual correction, and the next plan
> to be superseded will need another one.

## Goal

```
TEMPLATES = [{
    "BACKEND": "django_rust_templates.backends.RustTemplates",
    "DIRS": [BASE_DIR / "templates"],
    "APP_DIRS": True,
    "OPTIONS": {},
}]
```

works, in a project that has never heard of this package, with the finder **not
installed** — the stock installation every other Django template backend uses.

This is the user's stated requirement, restated after M18.0: *"It should be a
standalone Django template engine. It should follow the stock installation with the
`TEMPLATES` setting."* §2 of the design spec is titled "Why this is a rewrite of the
interface and not a rename" and says the same thing; §7 names this milestone. The
README's `install()` route is the *deprecated* one and now says so.

**The milestone is not a rename and not a new backend class in isolation.** It is the
work that lets the transcription exist without the finder that currently gives it its
name, its `__path__` and its identity.

## Global Constraints

- **The 1547 stays green under the finder, every task.** `scripts/run_django_suite.sh
  template_tests` is the oracle. §8's non-goal is explicit: the finder and `install()`
  survive as an opt-in developer mode, because without them the 1547 cannot run at all.
  So this milestone adds a *second* route to the engine; it does not remove the first.
- **The transcription contract is not weakened.** `scripts/check_transcriptions.py`
  permits a difference only inside a **declared region**, with executable lines named by
  a **snippet**, and never inside `COMPARED_PATH`. `_impl/base.py` already differs this
  way, so the mechanism exists; row 2 must use it rather than be granted an exemption.
  `scripts/gen_impl_transcription.py` writes "the pin plus a marker" and must learn the
  same declared transform, or the generator and the guard disagree and the next
  `--check` fails for the wrong reason.
- **`_impl` keeps its name.** Renaming to `django_rust_templates.engine` would churn
  every `# TRANSCRIBED:` marker, every anchor row and every test for no behavioural gain.
  Row 3's translation therefore targets `django_rust_templates._impl.*`.
- Pinned trees: `.django/` @ 6.0.9, `.venv/bin/python` 3.14.4. Every number above is
  against those.

## The hazard this milestone exists to avoid, stated before the tasks

**The same module can be registered under two names, and then there are two of every
class in it.** Under the finder, `_impl/defaulttags.py` is registered in `sys.modules`
as `django.template.defaulttags`. Standalone, it would be registered as
`django_rust_templates._impl.defaulttags`. If a translation is written unconditionally
one way, the *other* mode imports the file a second time, executes it a second time, and
produces a second, distinct `register` `Library` and a second set of node classes.
`isinstance` then fails across the two copies — and it fails *selectively*, only where a
value crosses the seam, which is exactly the shape that produces a green gate over a
broken engine.

Row 3's translation is therefore conditional on the mode, or the finder is changed to
alias `_impl` under both names. **Which of those two is the design decision of this
milestone**, and the choice has to be made once, in Task 3, with a test that can tell
the two modes apart (the discriminator is `__file__` and module identity — never
`__module__` or `type(v).__name__`, which print `django.template.base` in both modes).

The 16/16 false green in §2.2 is the precedent: a battery of cases passed against a
backend that parsed with stock Django's `Parser`. Nothing in a black-box render test
catches that; only identity does.

## Review Focus

1. **The mode-conditional translation (Task 3)** and its test. This is the load-bearing
   decision. A reviewer should ask: if the translation were hard-coded to the standalone
   name, which of the 1547 would go red? If the answer is "none", the test is not
   watching and the design is unproven.
2. **Whether the declared-region route leaves the diff readable.** 26 regions across 12
   files means 26 snippets a human has to read. If a reviewer cannot check one by
   reading, the declaration is the thing that has failed, not the code.
3. **That row 5 is not silently skipped.** Rust's four `import` calls are the ones a
   Python-only author will not think about, and they are the reason a backend can look
   self-hosted and still be served stock Django.

## Task 0: The inventory as a gate, not a paragraph

The table above is a measurement that will rot. Make it a script —
`scripts/check_self_host.py` — that, given a checkout and the pinned `.django/`, reports
row 1–2 and row 5's counts and exits non-zero when an engine-internal reference to
`django.template.*` appears **outside** a declared region.

It must print the sites (`path:line | <source line>`), not a total, for the reason
`.review`'s census work already established: a count that keeps changing is settled by
enumeration and never by an aggregation. Wire it into `--fast`.

*Verification:* run it on the current tree. It should report the inventory above and
fail. A guard that starts green here is measuring nothing.

## Task 1: `_impl` imports

Transcribe `django/template/autoreload.py` through the generator, in the same commit as
its `MODULES` row (§7's note on `loader_tags` is the precedent for why the row and the
file land together). Then take `_impl/__init__.py` to the point where
`import django_rust_templates._impl` succeeds.

Decide the ten fall-through modules one at a time, and record each decision:

- `autoreload.py` — transcribe. It is imported unconditionally by `__init__.py` and is
  three signal connections.
- `context_processors.py` — transcribe **only if** `RequestContext` needs it standalone;
  `_impl/context.py:7` names it by string, so it is on the path.
- `loader.py`, `response.py` — public API; transcribe if anything on the render path
  reaches them, otherwise leave fall-through and say so in the guard's exclusion list.
- `backends/*` — **do not transcribe.** `backends.py` replaces them. `loaders/cached.py:11`
  imports `copy_exception` from `backends.django`; that one function moves to our own
  module and the import becomes relative (row 2).
- `backends/jinja2.py` — never. It would add a jinja2 dependency to a package that has
  none, and §8 already declines the jinja2-backend tests.

## Task 2: the 26 imports, each in a declared region

Mechanical, but it is 26 declarations and the generator has to emit them. Extend
`MODULES` so a row can carry a list of declared line transforms, and teach
`check_transcriptions.py` to accept the regions the same table produces — one table, two
readers, so they cannot disagree.

Do it **file by file, one commit each**, smallest blast radius first (the eight
one-import files, then `loaders/cached.py`, `templatetags/i18n.py`, `engine.py`, then
`parser.py`'s ten). `parser.py` last because it carries the most and because a failure
there is diagnosable against a tree where everything else already works.

*Verification per file:* the 1547 stays green; `check_transcriptions.py` passes; the
Task 0 gate's count for that file reaches zero.

## Task 3: the name strings, and the two-names hazard

`_impl/engine.py:17-19` (builtins), `:40,42,43` (loaders), `_impl/context.py:7`
(`csrf`), `host.py:51-55`, `render.py:112,118`.

Resolve the hazard at the head of this plan **first**, then write the strings. Preferred
design, to be tested rather than assumed: the finder aliases `_impl` into `sys.modules`
under `django_rust_templates._impl.*` when it installs, so a single literal — our name —
is correct in both modes and there is exactly one module object per file. If that does
not hold, the fallback is a mode-conditional resolver, and either way the test is the
same: import a module in each mode and assert it is one object with one class identity.

*Verification:* a row that imports `defaulttags` under both modes and asserts
`sys.modules` holds one entry pointing at one file. This is the row that would have
caught §2.2.

## Task 4: `django_rust_templates/backends.py`

A `BaseEngine` subclass whose `Engine`, `Template`, `Context` and default loaders come
from `_impl` by our names. It must not import `django.template.backends.django` — that
module *is* Django's, and importing it would drag stock `django.template.engine` back
onto the path through `BaseEngine`'s own `self.engine = Engine(...)`.

`OPTIONS` maps onto our `Engine`'s parameters exactly as Django's backend maps onto
stock's: `context_processors`, `debug`, `loaders`, `string_if_invalid`, `autoescape`,
plus `libraries` and `builtins` as `Engine`'s kwargs. `DIRS` and `APP_DIRS` reach the
loader wiring, which is Task 5.

## Task 5: loader wiring

`APP_DIRS` and `DIRS` must build the same loader chain `_impl/engine.py:40-43` builds,
through **our** loader classes by our names. `cached.Loader` wraps by default when
`DEBUG` is false, and its `copy_exception` is row 2's relative import.

*Verification:* a template found by `APP_DIRS` renders identically through the backend
and through `install()`+`django.template`, byte for byte.

## Task 6: the proof — a stock project, in a venv, with no finder

`scripts/check_packaging.sh` gains the case that matters: a real project whose
`settings.py` names the backend in `TEMPLATES` and nothing else — no `install()`, no
`sitecustomize.py` — running `manage.py check` and rendering a page that uses
inheritance, `{% for %}`, `{% if %}`, a filter, `{% load %}` and escaping.

Two controls, without which the case is decoration:

- **The positive control is §2.2's own false green.** Re-run the 16-case battery that
  passed 16/16 against a stock-parsing backend. It must now **fail** — and the case
  asserts *that it fails*, with the failure naming Django's `Parser`. A case that only
  asserts success cannot tell the two engines apart, which is precisely how 16/16
  happened.
- **The negative control is the finder's absence.** Assert nothing on `sys.meta_path`
  comes from this package, and that `django_rust_templates.installed()` is false, while
  the render is still ours. Without it, the case passes whether or not the finder is
  there, and the milestone's whole claim evaporates.

## Task 7: README and `check_packaging.sh`, in the other direction

Only after Task 6 is green: the README's *Use* section loses the "not implemented yet"
caveat and the `install()` route becomes the developer-mode footnote it is. This is the
part of §7's M18.4 that belongs to this milestone, and it should not be written before
the case exists — a README that promises a working snippet is falsified by the packaging
gate in about ninety seconds.

## What this plan does not settle

- **Whether the render is Rust.** This milestone makes a backend *work*; how much of the
  tree is Rust-resident is §4's and M18.0's question, and slice 2's for-loop work is
  orthogonal and remains task #13.
- **§5's deletions.** Untouched; the finder survives (§8).
- **Performance.** The README's 1.35×–1.85× is unchanged by any of this. Making it
  faster is still the point of the project, and this milestone does not move it — worth
  saying because a backend that is clean and slow is not the goal.
