What Django's template engine does, and how much of it Rust does yet

The target is a drop-in replacement: Django's own template test suite, unchanged, running against templates rendered by Rust. Everything below is a Django feature. Done means Rust performs the work; in progress and to do mean Django's own Python still does, and the suite passes either way.

How to read the statuses

Done Rust does the work In progress Rust parses it, Django's code runs it To do still entirely Django's Not the engine Django's for good — an adapter around the engine, not the engine

Rust's parser drives every template, including the tags and libraries it does not implement: for those it hands the tag's arguments back to Django's own Python compile function. So a feature can work today, and appear in this page as not done, without contradiction. The honest measure of "ported" is the module count below — how much of the template engine still executes Django's code.

That count is over the engine, and it is smaller than the package it lives in. django.template holds the engine plus ten adapters — the loading facade, the backend registry and its five modules, template responses, context processors and the dev-server reloader. They are not the engine, they are not ours to rewrite, and they never will be: each one either wraps objects the engine already hands back or belongs to Django's view layer. They are marked Not the engine throughout, and they are subtracted from the meter rather than counted against it.

Tag and filter registration Done

What makes a template language extensible: the classes and decorators a project or a third-party app uses to add its own tags and filters. This was the engine's last module — library — and it is the engine's own rather than an adapter: {% load %} compiles a third-party tag library with it. It is now a faithful, verbatim transcription of Django's file rather than a reimplementation, because a tag library is Python by construction: simple_tag and its neighbours each build a compile function as a closure over the user's own function, and nothing on the Rust side can call it. What that buys is identity — Library, InvalidTemplateLibrary and the node classes are the same objects Django's own modules import, which is what the suite's isinstance and assertRaises rows are about. A reimplementation would have rendered the same output while answering those rows about the wrong class.

  • Library, registertag and filter registration API Library, @register.simple_tag, @register.inclusion_tag, @register.filter, SimpleNode and parse_bits are ours, transcribed from Django's file line for line. The parity harness runs twelve of the module's eighteen functions, so the transcription is compared against the pin rather than merely trusted.
  • Tags in Django's own libraries{% translate %}, {% blocktranslate %}, {% static %}, {% timezone %}, {% localize %}, {% cache %} All eighteen registered tags in the five django.templatetags libraries are compiled and rendered by Rust, and the nine filters those libraries register — localize, unlocalize, the four language_*, and localtime, utc, timezone — are on the Rust path too. Those last three hand off to the port's own Python transcription of do_timezone, which is one function serving all three names. The registration API above is still Django's — that is why this line reads as done while its neighbour does not, and why {% load %} still enters through Django's code.

Public template API Not the engine

The surface a Django project touches — the part "drop-in replacement" is judged by at the application level. Every item here is an adapter the engine sits inside: it hands the caller objects Rust already produces, and defines no template machinery of its own. These stay Django's, which is why they no longer appear in the to-do count.

  • Template loading facaderender_to_string, get_template, select_template Sixty-six lines and four functions, and every body is the same delegation: pick an engine, get_template(name), render(context, request). Both halves are already Rust's, so calling this facade already runs the port. It reads as ours at the application level for exactly that reason.
  • BackendsDjangoTemplates, Jinja2, Dummy The BACKENDS setting, per-backend OPTIONS, and the Template wrapper a backend returns. A protocol with a second implementation we deliberately do not provide — owning the registry would mean owning Jinja2's backend too. The suite reaches it from two rows only.
  • ResponsesTemplateResponse, SimpleTemplateResponse, render() The view-layer objects, including their caching and post-render hooks. HTTP semantics — status, Content-Type negotiation, pickling — that reach a template only through the loading facade above. Nothing in the engine imports this module; the import runs the other way.
  • Context processorscsrf, debug, request, auth Reached by import string from settings, not by import from the engine, so nothing in the engine depends on their identity. Every one takes a request and returns context for a response — view-layer machinery the engine merely names.
  • Template autoreloaddev-server template reloading Two signal receivers and a directory walk around objects that are already ours. Taking it would mean copying glue with no template machinery to get right — with nothing of ours to get right, there is also nothing for a test to falsify.

Not the engine Not the engine

Ten more modules of django.template are Django's own code and always will be. They are adapters around the engine rather than the engine: each one either wraps objects Rust already hands back, or belongs to Django's view layer, which reaches down into the template package rather than the other way round. They are subtracted from the meter rather than counted against it, and listed here so that anyone reading the module count can see where the other ten went. That list is read from §3 of the design document by the port's own tests, not restated, so the ten named there and the ten excluded from the count cannot drift apart.

How this is measured

Django's template test suite is pinned at 6.0.9 and run unchanged against the port; a feature is done when Rust performs the work and the suite is still green, not when a new test of our own passes. Alongside it is the port's own regression suite, which pins the invariants the port could otherwise break silently — the count of tests Django's discovery collects, which modules are still served by Django, and the line-level correspondence between the ported Python and the pinned original. The numbers on this page are read from the tree at each commit.

The acceptance run refuses to start unless both module counts are zero. Before the suite begins, every module the engine owns is imported and checked to be Rust's — all twenty-one of them, the sixteen under django.template and the five under django.templatetags — and a non-empty count stops the run rather than being printed beside it. The list of modules declared not the engine is read out of §3 of the design document by the port's own tests rather than restated here or in code, so the count cannot reach zero by quietly widening what it excludes.

The run also pins its own outcome. Its transcript is compared, as a whole line, against OK (skipped=6) after exactly 1547 tests, and the six skips are checked by identity — so a swap that keeps the total at six, a skip that appears, or a skip that stops appearing all stop the gate. The line is compared rather than dissected because a run may be green and still not this one: an expectedFailure that fails prints OK (expected failures=1) and exits 0, and no guard reading an exit status could catch it.

And it pins the checkout it runs against, before the suite rather than after it. The clone's head is read against the sha django.lock records, and any git status entry — including an untracked file planted in the tree — refuses the run. A transcript cannot tell you the Django it came from was stock, and a deliberately edited test is the one failure that every other check here would report as green.

Statuses describe which implementation performs the work, not whether a template using the feature renders correctly today: with Django's suite passing, most of what is marked to do already behaves as Django does, because Django is what runs it.
