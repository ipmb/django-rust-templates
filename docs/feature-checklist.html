What Django's template engine does, and how much of it Rust does yet

The target is a drop-in replacement: Django's own template test suite, unchanged, running against templates rendered by Rust. Everything below is a Django feature. Done means Rust performs the work; in progress and to do mean Django's own Python still does, and the suite passes either way.

How to read the statuses

Done Rust does the work In progress Rust parses it, Django's code runs it To do still entirely Django's Not the engine Django's for good — an adapter around the engine, not the engine

Rust's parser drives every template, including the tags and libraries it does not implement: for those it hands the tag's arguments back to Django's own Python compile function. So a feature can work today, and appear in this page as not done, without contradiction. The honest measure of "ported" is the module count below — how much of the template engine still executes Django's code.

That count is over the engine, and it is smaller than the package it lives in. django.template holds the engine plus ten adapters — the loading facade, the backend registry and its five modules, template responses, context processors and the dev-server reloader. They are not the engine, they are not ours to rewrite, and they never will be: each one either wraps objects the engine already hands back or belongs to Django's view layer. They are marked Not the engine throughout, and they are subtracted from the meter rather than counted against it.

Tag and filter registration Done

What makes a template language extensible: the classes and decorators a project or a third-party app uses to add its own tags and filters. This was the engine's last module — library — and it is the engine's own rather than an adapter: {% load %} compiles a third-party tag library with it. It is now a faithful, verbatim transcription of Django's file rather than a reimplementation, because a tag library is Python by construction: simple_tag and its neighbours each build a compile function as a closure over the user's own function, and nothing on the Rust side can call it. What that buys is identity — Library, InvalidTemplateLibrary and the node classes are the same objects Django's own modules import, which is what the suite's isinstance and assertRaises rows are about. A reimplementation would have rendered the same output while answering those rows about the wrong class.

  • Library, registertag and filter registration API Library, @register.simple_tag, @register.inclusion_tag, @register.filter, SimpleNode and parse_bits are ours, transcribed from Django's file line for line. The parity harness runs twelve of the module's eighteen functions, so the transcription is compared against the pin rather than merely trusted.
  • Tags in Django's own libraries{% translate %}, {% blocktranslate %}, {% static %}, {% timezone %}, {% localize %}, {% cache %} All eighteen registered tags in the five django.templatetags libraries are compiled and rendered by Rust, and the nine filters those libraries register — localize, unlocalize, the four language_*, and localtime, utc, timezone — are on the Rust path too. Those last three hand off to the port's own Python transcription of do_timezone, which is one function serving all three names. The registration API above is still Django's — that is why this line reads as done while its neighbour does not, and why {% load %} still enters through Django's code.

Public template API Not the engine

The surface a Django project touches — the part "drop-in replacement" is judged by at the application level. Every item here is an adapter the engine sits inside: it hands the caller objects Rust already produces, and defines no template machinery of its own. These stay Django's, which is why they no longer appear in the to-do count.

  • Template loading facaderender_to_string, get_template, select_template Sixty-six lines and four functions, and every body is the same delegation: pick an engine, get_template(name), render(context, request). Both halves are already Rust's, so calling this facade already runs the port. It reads as ours at the application level for exactly that reason.
  • BackendsDjangoTemplates, Jinja2, Dummy The BACKENDS setting, per-backend OPTIONS, and the Template wrapper a backend returns. A protocol with a second implementation we deliberately do not provide — owning the registry would mean owning Jinja2's backend too. The suite reaches it from two rows only.
  • ResponsesTemplateResponse, SimpleTemplateResponse, render() The view-layer objects, including their caching and post-render hooks. HTTP semantics — status, Content-Type negotiation, pickling — that reach a template only through the loading facade above. Nothing in the engine imports this module; the import runs the other way.
  • Context processorscsrf, debug, request, auth Reached by import string from settings, not by import from the engine, so nothing in the engine depends on their identity. Every one takes a request and returns context for a response — view-layer machinery the engine merely names.
  • Template autoreloaddev-server template reloading Two signal receivers and a directory walk around objects that are already ours. Taking it would mean copying glue with no template machinery to get right — with nothing of ours to get right, there is also nothing for a test to falsify.

Where Django's code is still running none

The number that moves when a feature really lands. Each module named here is still Django's, and the acceptance suite would pass with it in place — which is exactly why it is tracked. No module of the engine is left to name, and the acceptance suite runs entirely against Rust's code.

That last sentence used to be prose, and the place it was most likely to stop being true was the one file no gate read: django_suite/suite_settings.py names the BACKEND all 1547 tests run against, and it sits outside the tree scripts/gen_django_suite.py re-derives and diffs, so renaming that one string to Django's would have turned the whole acceptance run into a test of stock Django with every gate still green. It is now checked — that file, the alias engines["django"] resolves, and the seven adapter imports the vendored tree is allowed to keep, each asserted against a declared set in tests/test_suite_isolation.py and each re-derived against the pinned checkout there, so the set is inheritance rather than a licence this package granted itself. Prose became a refusal.

Ten more modules of django.template are Django's own code and always will be. They are adapters around the engine rather than the engine: each one either wraps objects Rust already hands back, or belongs to Django's view layer, which reaches down into the template package rather than the other way round. They are subtracted from the meter rather than counted against it, and listed here so that anyone reading the module count can see where the other ten went. How this is measured

Django's template test suite is pinned at 6.0.9 and run unchanged against the port; a feature is done when Rust performs the work and the suite is still green, not when a new test of our own passes. Alongside it is the port's own regression suite, which pins the invariants the port could otherwise break silently — the count of tests Django's discovery collects, which modules are still served by Django, and the line-level correspondence between the ported Python and the pinned original. The numbers on this page are read from the tree at each commit.

The acceptance run refuses to start unless both module counts are zero. Before the suite begins, every module the engine owns is imported and checked to be Rust's — all twenty-one of them, the sixteen under django.template and the five under django.templatetags — and a non-empty count stops the run rather than being printed beside it. The list of modules declared not the engine is read out of §3 of the design document by the port's own tests rather than restated here or in code, so the count cannot reach zero by quietly widening what it excludes.

The run also pins its own outcome. Its transcript is compared, as a whole line, against OK (skipped=6) after exactly 1547 tests, and the six skips are checked by identity — so a swap that keeps the total at six, a skip that appears, or a skip that stops appearing all stop the gate. The line is compared rather than dissected because a run may be green and still not this one: an expectedFailure that fails prints OK (expected failures=1) and exits 0, and no guard reading an exit status could catch it.

And it pins the checkout it runs against, before the suite rather than after it. The clone's head is read against the sha django.lock records, and any git status entry — including an untracked file planted in the tree — refuses the run. A transcript cannot tell you the Django it came from was stock, and a deliberately edited test is the one failure that every other check here would report as green.

Speed is measured, and is not yet a win. The port is checked against stock Django 6.0.9 and Jinja2 on 18 workloads × 2 modes = 36 rows in three families — micro templates that isolate one construct each, three "real-world" whole pages of increasing complexity, and the constructs that fall outside the three engines' shared syntax. scripts/bench.py --html writes docs/bench.html: charts, a table, and the provenance for every row. Each row hashes the bytes each engine rendered — 26 of 26 three-engine rows byte-agree, so the comparison is like for like rather than three different templates — and the harness prints the engine it built, the extension it loaded and which profile built it, refusing to print a table for any other engine. Measured 2026-10-09 local, the day the report stamps its run in UTC (2026-10-10 04:49): the port is 1.02× at render and 1.14× at parse on the real-world pages (geometric mean of three pages; the six rows run 0.95×–1.27×), and the worst row in the corpus is compile of a template that is almost nothing but the call — 2.23×, 8.81 µs against stock's 3.95 µs. Compatibility has been the priority throughout, and the measurement is published here rather than only the number that would flatter it. Every chart, tile and table block states which way "better" runs, and the word is read from the payload (bench.py's MODE_METRIC) rather than written into a caption, so a new chart cannot inherit the wrong direction silently. The fastest-engine tile is scoped for the same reason: counted over every row it used to read "django 19, jinja2 7", which reads as Django is faster, while Jinja2 wins every whole-page render at 0.30×–0.41× stock's time. Both are true; parse is where they invert, because Jinja2 compiles to Python source and Django does not.

The micro family's rows say how much of themselves is the call, because the old note claimed one family where there are two. Every row pays its engine's per-call overhead before it does any template work, and the overheads are not equal: measured, stock Django is 1.73 µs on a template that renders nothing, the port is 1.73 µs and Jinja2 is 3.45 µs. So bench.py measures that empty-template floor per engine and mode, prints it, and every table cell carries its call share — the floor as a share of that cell. The range settles the question the old note answered wrongly: over the micro rows it runs 2%–100%, so micro/text, variable, lookup, if, filter and escape are mostly a measurement of the call, while loop-text, loop-var, include and extends are a measurement of the construct — and on the real-world pages it never reaches 5% (0%–2% at render), i.e. those rows were never overhead-dominated at all. The floor is reported and not subtracted: a loop's own fixed setup is ~4.0 µs, not the 1.7 µs the empty template measures, so subtracting the floor would leave ~2.3 µs of loop setup inside a column claiming to be per-item work. (Both numbers are computed from the payload the table prints, not typed into a caption — the first draft of that caption said 51%–96% while the cells under it said 32%–100%.)

The compile floor was a per-parse Python set, not Rust work — and it is gone. Compilation was the port's worst row, and the cause turned out not to be in Rust at all: ShellHost.__init__ rebuilt its Rust-owned tag-name set on every parse, from three argument-free _native calls over registry tables that are compile-time constants. Nothing in that set varies per parse, so it is now a module-level constant — a pure speedup, not a behaviour change (the tests that read host._rust_owned still pass unchanged). Measured with the report's own instrument, the port's empty-template parse floor — compile plus render, the row the table prints — fell from 12.37 µs to 6.44 µs, i.e. 3.7× stock to 1.90×; compiled with no render at all (from_string("")) it fell 9.89 µs to 4.38 µs, 6.8× to 3.0×. The corpus's worst row, micro/text parse, went from 3.74× to 2.21×. Render is untouched — its floor is unchanged at 1.72 µs — because the hoisted set is read only on the compile path. The two compile figures are different estimators and are quoted apart deliberately: the report's parse mode is compile and render, so the ratio it prints for an empty template is about half the compile-only one. The table below is a single unpaired run, and it quotes slightly different digits for the same rows than a before-and-after pair does; the two are different statistics and are not meant to reconcile.

The filter-routing answer is now bound once per expression, not once per application. Every filter application asked the same question — is this handle one of ours? — and asked it by calling an accessor that re-derives and identity-checks its six source registries on every call: 1.074 µs each time, and a real-world page asks it 65 times in one render. Nothing in the answer depends on the argument, the value, or the context, only on the set of handles in the expression, so it is now computed on the expression's first resolve and kept in a fifth slot beside Django's four. That one site is what makes it work for both construction routes: the template compiler calls FilterExpression.__init__, while the Rust-side descriptor materialiser builds its objects with __new__ and never calls __init__ at all — and __init__ is deliberately left alone, since it sits inside a function the transcription harness executes, where an added line would compare Rust against Rust.

It is a win on the hot path and it was a loss on the cold one, until the fill was guarded. Measured as a same-harness A/B — two runs on each side of the commit, one machine, the extension's sha256 confirmed equal before and after, release build — micro/filter render fell 5.5/5.3 → 4.1/4.0 µs, real-world/normal 639.6/617.3 → 564.5/559.6 µs and real-world/complex 1311.6/1296.4 → 1199.4/1186.0 µs, against a Django control that did not move. But the report's two modes are not one instrument here: render compiles a template once and renders it repeatedly, while parse compiles a fresh one every iteration, so a cost paid once per expression is paid once per render in the first and once per iteration in the second. Measured in that second mode, real-world/large — ~300 expressions and not one filter — went 2900 → 3114/3469 µs while its render row did not move at all, which is the signature of a per-compile cost, and micro/variable parse rose 5.7%. Both are flat again now that the prologue runs only if self.filters: a filter-free expression pays a truth test, which is what it paid before. One row is still slower and is stated rather than hidden — a single-filter expression in parse mode (micro/filter parse, +1.9%), because the fill's import and slot miss cost about what the one accessor call they replace did. The win is on the hot path, where the answer is kept, and on expressions carrying more than one filter. The reviewer's companion suggestion — hoist the import out of the same loop — was not taken: it saves n-1 sys.modules hits on an n-filter expression, so nothing at all on the common one-filter case, and a reviewer's identical note was measured and reverted once already, which this repository's transcription guard records.

The render leaf's escape is Rust's now, and it was the largest single removable cost the profile found. Every {{ variable }} runs render_value_in_context, and for a plain str that meant template_localtime, localize and conditional_escape — a chain §1.3b priced at 0.79 µs of the 1.47 µs a variable cost, about 0.76 of it removable. The fast path is exact-str only, and deliberately not isinstance: a str subclass is where SafeString and markupsafe.Markup live, both carry __html__, and escaping one is the bug the predicate exists to decline. It calls _native.html_escape — the Rust escape the builtin escape filter already used — and takes the slow path unchanged for everything it declines. Measured as a same-harness A/B in which only engine/base.py differs (the control is that file at 8d1e74b — named, not HEAD, because HEAD moved the moment this slice was committed — restored afterwards by copy, so the tree is untouched and no git checkout is involved; the extension is the same build on both sides): micro/variable render 3.482 → 2.807 µs and micro/escape 3.485 → 2.793 — the 0.68 µs per variable §1.3b predicted, and 89% of what it called removable — real-world/normal 570.9 → 415.5 µs (−27.2%), real-world/large 871.0 → 689.5 (−20.8%) and real-world/complex 1211.4 → 1079.7 (−10.9%). Both modes move, and that is the signature to read: parse is compile and render, so a per-render cost shows in both rows while a per-compile cost shows only in parse — the inverse of the filter-routing row above. The port now beats stock Django on real-world/normal render (0.95×) and ties it on large (1.00×). On §1.2's own instrument — .review/m19-measurements/production_render_path.py §2, which is still in the tree — run against a control that is the same file at 8d1e74b, same extension (sha256:df7413aa6eeeb7b3), same interpreter, so only engine/base.py differs between the columns: 1.416 (N=50) / 1.385 (N=200) µs per variable before, 0.732 / 0.729 after — −48% — and the slice's number finally sits beside §2's prediction: 0.73 µs against a predicted 0.34. ~0.39 µs of the gap remains — 53% of it. Stock is ~1.07 µs either side, so ours/stock on this instrument moves 1.30× → 0.69× (medians over 5 rounds; ranges 1.274–1.305 and 0.678–0.693): the port now beats stock per variable, where before this slice it lost. The factor that is left is not overhead. On a template that renders nothing the port is 1.73 µs against Jinja2's 3.45 µs, yet Jinja2 renders every whole page 2.4×–3.4× faster — so the remaining gap is per-node work in the Python walk, which is what the native render walk is for. One compatibility gap was found on the way and was left to its own commit: of the 57 builtin filters, 47 render a str holding a lone surrogate ('\ud800') in stock Django 6.0.9 and raise UnicodeEncodeError in the port — upper, length, escape, striptags and the rest — and eight more raise a different exception from stock's, so only iriencode and urlencode agree at all, and they agree because stock raises on those two as well. The cause is the FFI boundary: a Rust &str is UTF-8, and a lone surrogate has no UTF-8 encoding. The fast path below declines that input rather than joining the set, so this change does not widen the gap — but the gap is real, it is wider than one filter, and it is repaired in its own commit below rather than inside a speed commit.

The next leaf down was the int, and it was the largest per-value cost in the engine — 3.42 µs, more than four times a plain str. Django's own numberformat.format has a fast path for exactly this input (if isinstance(number, int) and not use_grouping and not decimal_pos: return mark_safe(number)), but render_value_in_context reaches it through template_localtime → localize → number_format, and 3.0 of the 3.42 µs is get_language() and three get_format() calls whose answer that fast path then ignores. Those two statements run before the autoescape branch, so this is a placement question rather than a micro-optimism: the arm sits above both. Its predicate is the exact type plus context.use_l10n is False or not settings.USE_THOUSAND_SEPARATOR, and it declines in exactly the four settings states where grouping could change the answer — USE_THOUSAND_SEPARATOR on, with a default use_l10n, still renders '12,345' through Django's own path. Measured on int_fast_path.py (best of 7, one run, release extension): the same call falls 3.42 → 0.40 µs, and 28.9% of the values a real-world page resolves in this engine's own render are exact int — 385 of 1330, against stock's 185 of 1077 on the same corpus. A type defect was found on the way and is fixed rather than recorded. With autoescape=False, upstream's answer for an exact int is str(localize(value)), and str() is the identity on the SafeString that mark_safe(number) returned — so the answer is a SafeString unless use_l10n is False. The first version of the arm returned a plain str in both cases. No render of any template can see it (NodeList.render joins), the first draft of the probe ran one autoescape setting and printed agree on every row, and it took a (repr, type) comparison under autoescape=False to find. The row that pins it now asserts the type beside the characters across all eight settings states, and was confirmed to fail on the old code — six assertions, one per value — before it was kept.

The differential harness was reporting a green it had not earned, and that is worth a line more than the fix. It renders 48 cases through both engines and compares the results; 11 of the 48 resolve an int, and with settings unconfigured both engines refuse to render one — so those 11 columns were two ImproperlyConfigured reprs, matching because both engines read the same setting first. The case was covering nothing, and it said so only when the first setting read changed, which the int arm did. The harness now configures settings (48 of 48 identical, the 11 comparing '12345' against '12345'), and the divergence it exposed is pinned rather than hidden: a row runs both engines in a fresh interpreter with no settings and asserts that ours names USE_THOUSAND_SEPARATOR where stock names USE_I18N.

A value Django renders, this engine refuses — and the crossing is one line. Rust's &str is UTF-8 and a Python str is not, so crates/template-py/src/filters.rs:216's obj.cast::<PyString>()?.to_str() cannot hold a lone surrogate. Measured (census in surrogate_boundary.py): all 57 built-in filter names raised UnicodeEncodeError on '\ud800' — 37 of them take only the value and raise, the 20 that take an argument raise with one supplied — where Django's own body answers 33 of those 37. So {{ x|upper }} with x = '\ud800' raised here and rendered '\ud800' in stock; that was a drop-in divergence reachable from a public template today, not a step-2 risk. Repaired, and the repair pattern was already one function away. The seam now declines instead of raising: run_filter answers _native.CANNOT_HOLD, a singleton, and the builtin arm at engine/base.py:923 reads it by identity and falls through to the else branch that already existed for a name that is not a builtin — Django's own callable. Not None, because None is a filter's answer (default returns its argument; first/last return None for [None, 1]), so a None refusal would be indistinguishable from an answer — a row now asserts both readings off one call. And not a control-flow exception, though the reason first written for that was measured false: the draft said the render path's broad except Exception handlers would swallow it, and Django 6.0.9's VariableNode.render catches UnicodeDecodeError and nothing else (12 contexts — 6 template shapes × debug on/off — 0 swallowed). The reasons that hold are that a refusal is not an error, and that the sibling _native.html_escape already declines by returning. Measured after the repair: 37 of 37 value-only filters refuse at the seam (0 answered, 0 raised) and 20 of 20 argument-taking ones refuse with an argument supplied; 48 whole-template renders — 6 templates × 4 surrogate spellings × autoescape on/off — compare equal to stock, 0 diverge. Both halves are load-bearing: deleting the Python guard reddens 48 rows, reverting the Rust refusal 49. One leak was found in the first version of the repair and is worth the line: the sentinel was assigned into obj before falling through, so Django's own upper ran on it and {{ x|upper }} rendered &lt;the filter seam cannot hold this value&gt; — a leak that reads like a successful port. The result is a separate name, filtered, and obj is assigned only on an answer. Ordered before the walk and as its own commit, because the walk crosses this boundary per node and must know it crosses with a refusal path, and a correctness fix folded into a speed change makes the speed number unreviewable.

That figure holds only for an optimised build, and saying which build is now part of the harness. pip install compiles the extension with --release; maturin develop, which is what a development checkout runs, installs the unoptimised profile instead — and the first honest bench run after M18 measured that binary and produced 2.3× to 6.0× (2.34×, 2.49×, 4.69×, 6.01×), a range that says nothing about the port and everything about the build. It also went unnoticed for a while: the extension sitting in a working tree is whatever was last installed, so a stale or unoptimised one is invisible from the outside. bench.py now prints the extension it loaded and which build it is, beside the engine, and the real-world 1.35×–1.57× above is the figure for the --release build. The gate now builds it rather than trusting it: scripts/check.sh runs maturin develop --release before the Python suites, so the unit rows and the 1547 exercise the source instead of whatever happened to be installed. A row pins that invocation and its position — against every step that reads the extension, not one named step, since a build placed after any consumer cannot satisfy it — and the next line checks the claim behaviourally rather than textually: scripts/assert_native_is_the_built_artifact.py requires the _native the tests import to be byte-identical to the artifact the build just produced. (It lives in the source tree, python/django_rust_templates/, through the editable install — not in site-packages.)

It installs, and it refuses a Django it was not built for. pip install from a clone or a git URL builds the extension and installs an ordinary Django template backend; the wheel declares Django>=6.0,<6.1, and the backend refuses anything outside 6.0.x when Django builds it from TEMPLATES. Two measured outcomes are what the refusal is for, and neither is visible from inside this repository, where every check runs against the pinned checkout: against Django 6.1.2 the engine used to install cleanly, report an empty meter and render — every gate above would have said green — and against 5.2.7 it died with an ImportError that named Django. Both halves are checked in a real virtualenv by scripts/check_packaging.sh, which also installs the wheel with no Django present to prove the error is ours, and builds the source tree the way pip install . does. Switching it on is one setting — "BACKEND": "django_rust_templates.rust.RustTemplates" in TEMPLATES, with no "NAME" needed: the alias you reach it by is derived from that path as it is for every backend, and the module is named so that the derivation gives rust — and there is nothing else: no import to perform, no finder, no sitecustomize.py, no environment variable, and no ordering rule, because EngineHandler resolves that string the same way it resolves any other backend's. Nothing of Django's is replaced: the package has its own namespace, the engine is django_rust_templates.engine, and a name you reach across the boundary is Django's own object. The packaging check runs a real manage.py against a real settings module and asserts that the same project against Django's own backend renders identically; a control swaps the one line and must come out as stock Django. No wheel is published yet, so a source install needs a Rust toolchain; the port is also slower than the thing it replaces, which is the work in front of it.

The render walk landed, and it is the first thing that beats Jinja2 on a loop. A template that the Rust planner can render end to end — text, plain variables, and a {% for %} whose body is itself walkable — is now walked in Rust by _native.render_plan instead of by Python's NodeList.render. The plan is not sold as the win: M18.0 already measured that dispatch is not where the time is, and the minijinja study falsified the jump-table mechanism outright. The plan is what makes three removals reachable — the per-node Python frame, the per-iteration forloop dict that ForNode.render writes to the context and pops again, and the two render-invariant lookups below. Measured on scripts/bench.py, release extension, .venv/bin/python -I, one machine, the pre-walk tree built from the same checkout so only the extension differs: the real-world render geometric mean against stock goes 0.765 → 0.583, and the loop rows are the reason. micro/loop-text render falls 15.4 → 3.7 µs — 0.25× stock, against Jinja2's 5.6, so the row closes on Jinja2, which is the acceptance line this slice was held to. micro/loop-var render falls 69.3 → 20.3 µs (0.25×; Jinja2 33.3), and real-world/large render 483 → 220 µs (0.32×). Output is unchanged: every row of the three-engine intersection is byte-identical to stock's, which the benchmark's own equality gate asserts rather than the report asserting it.

Two per-render costs were found by measuring, not by reading, and both are gone. The walk's fixed cost was 1.2 µs above Python's path on a template that renders one text node — invisible in the loop rows, where a per-iteration win dominates, and the whole of the micro/text row. Splitting the call showed _native.render_plan itself at 0.656 µs for an empty plan, and the split further showed where it went: the escape function and mark_safe were each an import plus a getattr per render. Both are now resolved once per process through PyOnceLock. The larger half was the constructor choice: mark_safe("") costs 0.484 µs and SafeString("") costs 0.072 — mark_safe is Django's public helper, wrapped in keep_lazy_text, while the expression being replaced, NodeList.render, constructs SafeString directly. The faithful call is also the fast one. The empty-plan render_plan is now 0.221 µs, micro/text render is 1.9 µs against stock's 1.8, and the walk costs essentially nothing on a template it cannot win on.

The walk now owns a filtered expression and an {% if %}, and that is what lets a loop seal. A {{ x|filter }} whose chain Rust can name is walked instead of handed back, and an {% if %} whose condition is a bare lookup is walked too; an operator condition still delegates, as before. Each is small on its own — but a loop body is sealed only if every node in it is walkable, so one filtered variable or one delegated {% if %} anywhere inside a loop used to hand the whole loop, and the whole table it builds, back to Python. Measured on the pre-change tree and published as a prediction before the run (.review/m19-measurements/step3a_prediction.md): the corpus's real-world/normal with its two {% block %}s spliced away goes from 98.2% of its output returned from Python to 0.7% — the 41 characters of the footer and nothing else — with the loop's ForNode moving from delegated to walked and the walk's visit count on that page going 11 → 618. The two constructs' own rows each pass parity in render (1.23× → 0.95× for the {% if %}, 1.06× → 0.87× for the filtered variable), the real-world render geometric mean against stock goes 0.58× → 0.55× (parse 0.94× → 0.90×), and the rows that cannot move — anything whose body sits behind a {% block %}, and a loop body holding {% cycle %} or a forloop read — do not move, which is the prediction's other half. One honest flat: the {% if %} parse row is unchanged, and the reason is measured rather than asserted. A parse row is from_string plus a render, so the claim decomposes: on that row the compile path is 22.2 µs against stock's 10.8 and the render 2.31 against 2.42, so essentially all of the 11.3 µs measured gap is compile — a path this change never touched — and the render path is 0.11 µs ahead of stock's on that row.

What is left, stated against the same table. The single-node parse rows are still ~1.4×–2.3× stock — that is the compile path, not the render path, and it is the next leaf (materialising Python node objects eagerly). micro/include (0.70× stock, 7.0 µs against Jinja2's 6.0) and micro/extends (0.98×, 9.7 against 5.2) are the two rows Jinja2 still wins outright: it precompiles {% include %} into the parent, and this engine still opens a Python frame per include and per inheritance level, which is what step 5's second slice is for. django-only/filter-arg remains the one row both slower than stock (1.10×) and outside the three-engine intersection — Jinja2 spells a filter argument floatformat(2), not floatformat:2, so the row runs on two engines.

A bare number in a filter argument was the one shape the walk silently declined, and that is now fixed. Django parses a filter argument three ways, not two: {{ r|floatformat:2 }} is stored as (True, Variable("2")) — a variable argument, because digits are in var_chars — and Variable turns that into a literal rather than a context lookup, which is Django's deliberate design so the number keeps its type when it reaches the filter. The walk read "no lookups" as "not mine" and handed the node back, so every such expression was delegated whole while the node count still reported the row as covered. Carrying the literal instead takes django-only/filter-arg from 99.4% of its output returned from Python to 0.0%, its render ratio from 1.39× to 1.10× of stock and its parse from 1.40× to 1.13×, and the django-only family's geometric mean from 0.77× to 0.74× — with the acceptance tiles unmoved (real-world render 0.55× → 0.54×, parse 0.90×). The literal has to be the int and not its text: marking it safe would stringify it, and floatformat:2.5 is where the two part company (1.23 against 1.2345). The corpus holds exactly two such arguments, and the other one — inside a {% block %} in django-only/realistic — does not move, because the block above it is delegated whole; that is reachability rather than argument shape, and it is the next slice.

The walk now owns a {% block %} body, and on the page that is all body that is the whole render. A descent pass in Rust plans the body nodelist of every {% block %} it can and attaches that plan to the NodeList itself, and BlockNode.render renders that body through the plan instead of through Python. ExtendsNode and BlockNode stay Python delegates — this slice takes the body, not the inheritance machinery — and the numbers say the body was the thing: real-world/normal's render ratio goes 0.89× → 0.31× of stock (373 µs → 129 µs against stock's 417), its parse 0.99× → 0.55×, measured on two runs of one artifact. The gate is the census, and it is the same page measured two ways: real-world/normal now reads applied: length=2 upper=1 title=50 and body xings: 50 — identical to the spliced fixture flat/normal that step 3a used as its ceiling, down to the filter counts. The 50 matters more than the applied: line: routed-but-not-computed is exactly what a share meter cannot see, so the third meter from step 3a is what certifies this one.

And it is honest about where it does not pay, which is the other half of the prediction. micro/extends moves only 1.04× → 0.98×, because its bodies are three and four nodes and the render is two Python frames and a get_nodes_by_type walk over the whole parent — a body plan does not touch any of that. real-world/complex (0.62×) and django-only/realistic (0.93×) do not move at all, and the census says why before the timings do: their loops hold an {% include %} and a {% blocktranslate %}, a body holding a delegate cannot seal, so the whole loop is delegated and the walk never reaches inside it. Their output-returned-from-Python share rises — 298.8% → 494.5% and 197.8% → 295.0% — which is the correct reading of moving work out of a frame a share meter cannot see inside. Both were predicted to move and both predictions are recorded as misses rather than reworded. real-world/large, the control with no inheritance at all, is identical in every census column and every timing, as predicted.

One design change against its own prediction, made because the guard refused the first one. The prediction put the arm inside NodeList.render. It cannot go there: that function is on the transcription guard's compared path — the set tests/parity_target.py reads to decide whether a declared transcription region sits on code the parity harness executes — and a region there would make the harness compare Rust against Rust. So the arm became a new method (_render_with_plan) and the hook moved to its caller, BlockNode.render, with that file's two lines rewritten by the generator's TRANSFORMS table so it stays generated and its seven compared-path spans stay bit-identical. The scatter band is stated before the deltas it bounds, as every slice since step 3a has: two runs of the one artifact give a median 1.08% and a max 8.43% over all 36 ratios, so nothing under ~2% is called a move here — and the real-world/normal row is 60× the band. Acceptance is unmoved and verified on this artifact: 1547 tests, OK (skipped=6), plus the 494 unit tests.

Until M18 it was a substitution, and that machinery is gone. Earlier revisions of this page described a meta-path finder that served a transcription of django.template under Django's own module names, switched on by an install() call placed before django.setup() ran — which is why this page used to argue about manage.py versus settings.py. That whole apparatus (_shim.py, _impl/, install(), scripts/shimpath/) was deleted, and the acceptance suite it existed to drive in place was replaced by a copy of Django's template_tests vendored at django_suite/ and regenerated by scripts/gen_django_suite.py. The same 1547 tests run; they simply import this package's engine by name instead of being tricked into it.

Statuses describe which implementation performs the work, not whether a template using the feature renders correctly today: with Django's suite passing, most of what is marked to do already behaves as Django does, because Django is what runs it.
