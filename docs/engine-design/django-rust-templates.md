# django-rust-templates — Architectural Design

## 1. Overview

This repository reimplements the Django Template Language in Rust and ships it as an ordinary Django template backend, named in a project's `TEMPLATES` setting like any other. It is a transcription of one pinned Django version rather than an independent implementation, and the backend refuses to run against a Django it was not transcribed from. The language is unchanged: same syntax, same tags, same filters, same output bytes.

Three pieces:

- `crates/template-core` — the engine proper. It has no Python dependency; everything that must reach the host language is a trait (`parser/host.rs` for tags and filter binding, `filters/host.rs` for filter bodies).
- `crates/template-py` — the PyO3 binding. It implements those traits over Python objects, and is the only crate that links PyO3. It exposes the `_native` extension module.
- `python/django_rust_templates/` — the Python shell. `engine/` is a line-for-line transcription of `django/template/`, carrying Django's node classes, context, filters, library machinery and loaders; `host.py` and `render.py` are the shell's half of the FFI seam; `rust.py` is the backend class.

The split of work: Rust lexes and parses every template; Python owns the node tree that renders; Rust renders the part of that tree it can prove it reproduces, and hands the rest back to Python.

## 2. Compilation Pipeline

| Stage | Entry point | Produces |
| --- | --- | --- |
| Segment | `lexer::segments` | the source split at `{% %}`, `{{ }}`, `{# #}` |
| Lex | `lexer::Lexer::tokenize` | a token vector |
| Parse | `parser::Parser::parse` | a `NodeListDesc` — plain data, no Python |
| Host tag | `Host::call_tag` → `ShellHost.call_tag` | one `NodeDesc`, plus the tokens the tag did not consume |
| Materialise | `materialise_native`, falling back to the Python `materialise` | a Django `NodeList` of real `Node` objects |
| Plan | `plan_list` | a `NativePlan`, or nothing |
| Assemble | `template_for` | a `Template` |

`_native.compile_template` drives all seven. It is reached from `render.parse_template`, which `Template.compile_nodelist` delegates to, so every template in a configured project takes this path.

Lexing is a single pass over segments with an alternating in-tag flag, matching Django's regex split; `{% verbatim %}` is lexer state. A debug flag decides whether tokens carry character offsets, and it is read from the engine's own `debug` attribute at compile time, as upstream does.

Parsing is a port of Django's loop: the token vector is reversed so taking the next token is a pop, dispatch is on the raw first word of the tag contents, and reaching a `parse_until` name prepends the terminator and returns for the caller to consume. The result is not Python — it is a descriptor tree with no trait objects, no lifetimes and no Python objects in it.

Materialisation turns that tree into Django's node classes by name. It runs in Rust by default, with the Python decoder retained for shapes the Rust path does not build and for host-owned nodes.

## 3. Runtime Representation

A compiled template carries three things.

The **descriptor tree** (`NodeDesc`, `NodeListDesc`) is what the parse produced: a Python class name, constructor arguments by parameter name, child nodelists, and an optional reference-table slot. Unlike a conventional IR it is not consumed and discarded — it is kept, because the render plan is built by walking it alongside the node tree built from it.

The **node tree** is Django's. `Template.nodelist` holds real `Node` instances and `NodeList.render` is upstream's. This is what renders whenever nothing faster applies.

The **plan** (`NativePlan`) is a flat list of slots. Each slot pairs an action — emit text, emit an expression, an `{% if %}`, a `{% for %}`, an `{% include %}`, or delegate — with the materialised Python node it was planned from. The pairing is asserted rather than assumed: if a descriptor's class name disagrees with the object at that index, no plan is produced for that list at all. Plans are attached to the `Template` and to the body `NodeList` of each `{% block %}`.

`Template._render` tries the plan and falls back to `nodelist.render` when there is none, or when the native walk returns nothing. `BlockNode.render` does the same one level down, through the nodelist's plan-aware render method.

## 4. Language Model

The language is Django's, unchanged — see `django-templates.md` in this directory for it. What differs is where each construct is compiled.

- Nearly all of Django's built-in tags have a Rust compile function. Two are deliberately excluded and a test asserts their absence: `{% load %}`, whose compile mutates parser state that later tokens must see, and `{% querystring %}`, whose compile function is generated by `simple_tag` and is therefore Python's.
- The tags from Django's own `cache`, `i18n`, `l10n`, `static` and `tz` libraries are compiled in Rust too, but only behind a `{% load %}` — the parser asks the host whether the library was loaded before consulting its own library registry, because a tag used without its `{% load %}` must still be refused.
- Every built-in filter has a Rust body, as do the filters those five libraries register. The Python transcriptions of all of them remain, and are what runs whenever the native path is not taken.
- Everything else — a third-party library's tag, a `simple_tag`, an `inclusion_tag`, a custom filter — is compiled by Django's own code through the host seam and renders through its own `render` method.

The rule for what Rust compiles: a tag is Rust's if its compile function is a function of the token and the parser's structural cursor alone. A tag whose compile reads or writes host-side parser state whose lifetime is the parse rather than the node belongs to the host.

## 5. Variable Resolution and Data Model

The resolution loop from `Variable._resolve_lookup` is ported to Rust; the host supplies each arm through a `LookupTarget` trait implemented over Python objects. Keeping the loop in Rust is what makes arm order and the swallowed-exception sets testable without an interpreter.

The arms are Django's, in Django's order: subscript (guarded by a `__getitem__` check on the type), then attribute, then integer index, with `dir()` consulted only for a swallowed attribute-arm exception. The callable arm is three-way — call it, leave it alone for `do_not_call_in_templates`, or substitute `string_if_invalid` for `alters_data` — because the three produce three different values. `string_if_invalid` is read lazily, at each substitution site, since reading it up front raises when no template is bound.

Filter values cross the seam as a `Value` enum: `None`, booleans, integers (with a separate arm for values outside a machine integer, carried as canonical decimal text), floats, strings, safe strings, lists, and an opaque handle into a per-call interner for everything else. Safety is one variant carrying both the text and the marker, rather than a string plus a flag, so a filter body cannot return the text while dropping the marker. A value Rust cannot hold — a string containing a lone surrogate, for instance — returns a sentinel rather than an error, and the application is redone in Python.

Four modules exist because Python's primitives are not Rust's, and each is pinned by an exhaustive cross-language comparison rather than computed from one side:

- `pyunicode` — Python's whitespace table, which includes the information separators U+001C–U+001F that Unicode's `White_Space` property does not, plus Python's uppercase mapping.
- `pyregex` — Python's `\w`, which is `str.isalnum()` plus underscore and does not match the `regex` crate's.
- `pynum` — Python's `int()` and `float()` grammar, including underscores between digits and non-ASCII decimal digits.
- `pyposix` — `posixpath`'s `join`, `normpath` and `dirname`, which differ from `std::path` on cases templates hit.

The Unicode tables move with the interpreter, so the matching set is selected when the extension module loads, from the running interpreter's own Unicode version.

## 6. Context and Scoping

`Context`, `RenderContext` and `RequestContext` are Django's, transcribed verbatim. Nothing about scoping is reimplemented: the context is a stack of dicts, writes go to the top frame, and scope isolation is opt-in exactly as it is upstream.

The native walk does not reproduce the context managers either — it calls them. Pushing a layer, pushing render-context state and binding a template are each performed by entering the real Python context manager, so a `RequestContext` still runs its processors at bind time and a `Context.push` override is still seen. The exceptional exit path is preserved, including the generator-based manager semantics that let a body's `finally` observe the in-flight exception.

The one place the walk writes the context itself is `{% for %}`, where it builds the loop dict and stores the loop variable per iteration in Rust. That is built only for a loop with a single variable: an unpacking loop writes one entry per name and the order between them is observable, so it is declined rather than approximated.

## 7. Template Composition

`{% extends %}`, `{% block %}` and `{% include %}` are compiled in Rust and rendered by Django's transcribed loader tags. Relative `./` and `../` template names are resolved during the parse, over the `posixpath` port.

Inheritance stays Django's at render time. The extends node always delegates, because block resolution is a stack of per-name queues in the render context that the walk does not model. What the walk does instead is plan the *body* nodelist of each `{% block %}` it can read, since on a page that extends a parent that body is where the render time goes. The plan is attached to the nodelist rather than to the node, because the node that renders a body is frequently not the node the plan was built from — `BlockNode.render` renders an override popped out of the block context, and `{{ block.super }}` re-enters through the parent's own block, but all of those paths share the one body nodelist.

`{% include %}` is planned only in its simplest shape: a constant name, no `with` bindings, no `only`. Before rendering the target itself, the slot checks that the target's `render` and `_render` are the two functions the engine defines, captured once at import; a `Template` subclass or a rebound method declines the slot and the include returns to Python. Where a loaded template is cached stays Django's business — the per-render-context cache on the include node.

Partials cross to the host mid-compile, because both halves read parser `extra_data`: the definition registers a body that outlives the parse, and the reference holds a live view of that dict which is only subscripted at render time, so a reference may precede its definition.

## 8. Escaping and Safety

Django's model is the authority. `SafeString`, `mark_safe`, `conditional_escape` and `SafeData` are imported rather than reproduced — notably because `markupsafe` exposes `__html__` without inheriting from `SafeData`, and `conditional_escape` treats the two differently.

On the Rust side safety is carried in the type: a distinct wire variant for an already-safe string, and a distinct `Value` variant across the filter seam. The walk inlines only the first arm of `render_value_in_context` — the case where the value's type is exactly `str` under autoescaping — and calls Rust's escape there. A `str` *subclass*, which is where `SafeString` lives and which carries `__html__`, falls through to Django's function. An escape Rust declines to perform falls through the same way.

Autoescape state and the escape function are read once per render rather than once per node. This is only a timing difference: `{% autoescape %}` compiles to a node the walk delegates, so a block that changes the flag is rendered by Python.

There is no sandbox, as in Django: a template reaches whatever is reachable from the objects in its context.

## 9. Extensibility

| Extension point | Can do | Cannot do |
| --- | --- | --- |
| `register.tag` / `register.filter` | everything they do under stock Django; compiled through the host seam | be compiled in Rust, or be rendered by the native walk |
| `{% load %}` | shadow a built-in name — the host compares the registered callable's identity against Django's own, so a loaded library wins | be compiled in Rust, since its own compile mutates parser state |
| `OPTIONS["builtins"]` | make a library global, and take a name away from Rust at engine construction | — |
| Loaders | supply origins and source from any medium, including the caching loader | affect parsing |
| Context processors | inject request-derived values, through the real `bind_template` | run outside a `RequestContext` |
| Parser `extra_data` | pass compile-time data to the `Template`, partials included | be read during another template's parse |
| The backend class | accept everything `DjangoTemplates` accepts, plus the option that waives the Django version check | be activated other than by being named in `TEMPLATES` |
| Rust tag and filter registries | — | be extended at runtime; they are static tables |

The backend subclasses Django's own `DjangoTemplates` as a marker, not an inheritance — every method is overridden. The subclass exists because Django and its ecosystem ask `isinstance` to find the DTL backend: the admin's system checks and the template autoreloader both return early otherwise.

## 10. Error Handling and Debugging

Rust raises one exception class for everything a parse rejects, with a subclass for an unimplemented construct. The shell chooses the Python exception object: Rust owns the message, Python owns the class, because message assertions, the debug-annotation path and Django's parallel test runner all inspect the object rather than the text.

When a *host* tag's own code raised, the exception is re-raised by identity rather than rebuilt from a name and a message — the shell stashes the instance on its way out and the conversion matches it by class. That mirrors Django's own parser, which re-raises the object it caught, and it is what preserves the traceback and any culprit-node annotation already attached.

Tokens cross the seam as fixed-shape tuples and are turned back into Django `Token` objects on the Python side, which is what makes the token on a raised exception usable by the debug-info builder. Character positions exist only under the debug lexer, selected from the engine's `debug` flag; with the plain lexer the annotation path would fail inside its own exception handler.

The native walk reproduces Django's annotation protocol rather than skipping it: it builds the debug info for the node that was rendering, and a delegated node goes through `render_annotated` so the protocol has one implementation. Recursion is capped twice — once on plan nesting depth and once on nested native render calls — because CPython's recursion limit protects the Python stack and not the Rust one. Exhausting the frame budget returns nothing and the remainder renders in Python.

## 11. Performance Characteristics

Figures live in the benchmark report the `scripts/bench.py` harness produces, not here; what follows is where the costs are, which outlasts any particular number. The harness renders one corpus through stock Django, this engine and Jinja2, in three modes — compile only, render only, and compile-and-render — and hashes every row's output per engine. A byte difference from stock Django is a hard failure, because drop-in equivalence is the criterion the project rests on.

**Render.** The walk removes, per node, the `render_annotated` → `render` Python call pair and the intermediate string each nodelist joins: it accumulates into a single Rust buffer and builds one safe string at the end. Per iteration of a planned loop it removes the loop-dict construction and the loop-variable store. Per render it hoists the autoescape and escape-function reads out of the node loop and inlines the plain-string escape arm, so an unfiltered variable reference costs no Python frame.

**Declines are total.** A node the walk cannot plan, a filter whose function is not Django's own, a loop with tuple unpacking, an `{% if %}` with an operator condition, an include with bindings or isolation — each renders on the Python path, unchanged. A declined plan is a lost optimisation and never a different answer, which is why a mismatch produces no plan rather than a partial one. The consequence is that fast-path coverage is a set difference nothing in the output reveals, so the extension exposes a census of which node classes the walk handled, which it delegated, and which filters it applied itself.

**Compile.** The dominant cost is not the parse — it is building the Python object graph the parse describes. A materialiser that walked a serialised wire of nested tuples spent the bulk of a compile decoding it, which is why the wire is now built only on the fallback path and the nodes are constructed directly from the descriptor tree. The plan built from that same tree is cheap by comparison.

**The host seam is linear per call and quadratic per template.** Calling a host tag hands the shell every token the parser has not yet consumed and takes back whatever is left, so a template with many host tags copies the remaining stream once per tag. Templates that use only built-ins never pay it.

**Caching** is Django's. The caching loader is transcribed and on by default, so parse cost is paid once per process per template name; the plan is built during that compile and lives on the cached `Template`.

## 12. Design Decisions

| Decision | Rationale | Consequences (+) | Consequences (−) |
| --- | --- | --- | --- |
| Transcribe one pinned Django rather than reimplement the engine from its documentation | correctness rests on reproducing one version's behaviour, and that version's own test suite is the gate | Django's semantics are present even where Rust has no port; each transcription's diff from upstream is mechanically checkable | a Django bump is a re-transcription; the backend refuses other versions outright |
| `template-core` has no Python dependency; the host is a trait | engine semantics stay testable in a bare shell, with no interpreter, venv or built extension | a tag or filter can be proved in isolation | two implementations of each seam, plus null and scripted stand-ins for tests |
| Rust parses; Python owns the tree that renders | binding a filter needs `inspect` over a Python function, and third-party tags return Python node objects | every existing tag, filter and node class keeps working unmodified | a descriptor layer between the two, and a materialisation step on every compile |
| Host-owned values cross by opaque handle | Rust must not read a Python object it cannot model | the parse is reproducible without Python, and identity is preserved for nodes two tags share | a handle is valid only within the parse or the filter call that minted it |
| The native walk declines by default: a descriptor and a node that disagree produce no plan | a wrong plan is a wrong render, and a wrong render here would be invisible | a misread node costs speed, never correctness | fast-path coverage is observable only through the census |
| The walk calls Django's context managers rather than reproducing them | `bind_template` and the render-context state manager have observable bodies that subclasses override | overrides and generator-based manager semantics survive | measurably slower than calling the underlying bodies directly |
| One Rust exception class, converted on the Python side | Rust owns messages; the exception *object* is what Django's tooling inspects | message assertions, debug annotation and pickling across test processes all work | one conversion point that has to know about host-raised exceptions |
| A host tag's exception is re-raised by identity | Django's parser re-raises the object it caught | traceback and culprit-node annotation survive | the shell must stash the instance, since only the class name crosses the FFI |
| Python's tables are ported, not approximated | Rust's whitespace, `\w`, integer parsing and path handling each differ from Python's on inputs templates actually hit | exact parity on tag stripping, filter names, numeric literals and relative paths | generated tables pinned by exhaustive cross-language tests, re-checked per interpreter version |
| The package has its own namespace and patches nothing | an earlier design substituted itself for `django.template` on the import path, which made registry objects ambiguous | names reached across the boundary are Django's own objects, behaving as they do for any backend | the engine is reachable only through the `TEMPLATES` setting |

## 13. Deliberate Non-Goals

- **No language changes.** No new tags, filters, delimiters or expression syntax. Byte-identical output is the acceptance criterion, checked by Django's own template test suite and by the benchmark's equality gate.
- **No sandbox.** Attribute access is as unrestricted as Django's.
- **No streaming output.** A render materialises the whole string, in Rust or in Python.
- **No async rendering.**
- **No Rust extension API.** The tag and filter registries are static tables; a project extends the engine in Python, exactly as it does under Django.
- **Not a fork and not a patch.** No module of Django's is replaced, shadowed or monkey-patched; `django.template` stays live for every other caller in the process.
- **No multi-version support.** The engine reproduces one Django's behaviour and is proven against that one only, so running it against another is refused rather than attempted.
